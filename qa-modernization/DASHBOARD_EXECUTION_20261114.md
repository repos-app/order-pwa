# QAダッシュボード：実行指示と非同期キュー（2026-11-14）

## 操作

Windows PCの `http://127.0.0.1:18765/` を開き、通常の5分類画面の「テストを実行」から指示する。

1. **全件実行**：対象の分類を「自動テスト全体」「npm」「業務」「WEB」から選択。全体は現在324ケース＝npm230＋業務49＋WEB45。分類内はケースごとに直列処理し、個別FAILでも次を続行する。
2. **失敗だけ実行**：現在の独立証拠でFAILになっているケースだけを実行する。証拠が古くなったSTALE_SOURCEは失敗と見なさない。対象が0件なら開始ボタンを無効にする。
3. **チェックしたケースを実行**：分類カードから詳細を開き、テスト名の左側にあるチェックで選択。検索やページ送り、複数分類をまたいで選択できる。全対象を確認して実行する。

いずれも開始前に件数を提示する確認ダイアログが出る。指示受理後、ブラウザはテスト完了を待たずにジョブIDを受け取り、4秒間隔で実行数・PASS/FAIL・実行不可・証拠失効を再取得する。「ケース別の実行結果・ログを確認する」から各ケースの最終結果と実行ログを参照できる。

## 既存資産との統合

- **npm**：登録済み `test/project-test-commands.json` の `PIPE-###` のみ、既存 `scripts/run-project-test-pipeline.mjs --dashboard-case=PIPE-###` を実行する。実際の終了コード、開始/終了時のソース指紋・既存証拠スキーマを照合。登録外コマンドは通さない。単発実行の証拠は `scope=dashboard` として既存npm証拠リーダーに登録し、他のケースの古い証拠を勝手に有効化しない。
- **業務**：同じS4ケースIDを既存ランナーで SQLite と隔離Worker/D1 に各1回実行し、2環境の独立証拠がPASSした時だけケース1件をPASS。いずれか失敗しても次の業務ケースへ継続する。
- **WEB**：S2/S5/S6の既存Chromium .test.mjs を実行。複数テストを含むファイルはケース別の `--test-name-pattern` を使い、既存のPNG・API・独立SQL・cleanupとソースSHAでPASS判定する。S5-REFUND-007とS5-PAYMENT-CORRECTION-010は同一の複合テストが証拠を作成する。
- **実機自動**：現在の5分類では対応する現行ランナーが未連携、登録0件。実行できたふりをしない。旧正式1659件を加算しない。
- **ユーザー本人実機**：別ページの60件は本人がOS・ビルド・端末を指定して実タップした結果を記録する。自動コマンドでPASSを付与しない。

## サーバー・証拠・安全策

- `GET /api/qa-run-jobs`：進捗・最後のジョブ・最近の履歴
- `POST /api/qa-run-jobs`：`{mode:'all'|'failed'|'selected',category:'all'|'npm'|'business'|'web',caseKeys?:string[]}`、ブラウザの明示ユーザー操作、JSON、`Origin` 一致、`X-QA-Execution: explicit-user-action` が必須
- `GET /api/qa-run-jobs/log?jobId=...&caseKey=...`：ジョブ所属・正規化済みケースのログ末尾（上限96KB）
- 永続記録：`test-results/qa-dashboard-execution/jobs/*.json`、`logs/<jobId>/*.log`。ここは正式QA台帳ではない
- worker：`scripts/qa-modernization/dashboard-execution-worker.mjs --lane=npm|business|web|all`。実行依頼後にWindows PCで非表示の独立Nodeプロセスを起動し、ダッシュボードの再起動や画面離脱でも処理する。分類別の排他ロックにより同分類の重複実行を防止する。既存の `worker.lock` は、修正前から実行している旧ワーカーの識別にのみ使用する
- 進行中のworker異常終了時、実行途中だったケースは `BLOCKED: WORKER_RESTART_INTERRUPTED_UNVERIFIED` として再開し、証拠のないPASSを付けない。未着手ケースは継続する
- フォーマット不正、未登録ID、任意のコマンド/ファイルパス、クロスオリジン、**同一分類が重複するジョブ**の投入は拒否する。異なる分類（npm／業務／WEB）は同時投入・並行実行が可能。混合・全体ジョブは対象に含む分類すべてを占有する

## 検証・運用上の注意

ジョブ送信→HTTP即時応答→別Nodeプロセスがテスト実行→npm証拠ファイル/ログ生成→独立判定・完了まで、ローカルの `PIPE-006` で実際に1件PASSを確認した（正式実機QA PASSではない）。

定義済み全324件を現時点で通し実行したわけではない。自動ランナーの本体に外部依存がある場合は個別ケースがFAIL/BLOCKEDになる。ユーザーの本番店舗データを変更するテストは追加しておらず、既存の隔離Fixtureを再利用する。分類内では順次処理し、別分類は専用ワーカーで並行実行できる。変更前から実行中のレガシーワーカーは中断せず、起動時刻以前のジョブを保持する。
