**ACTIVATED IN SOURCE:** `mobile-app/web/config.js` now sets `AUTH_REFRESH_RESPONSE_RECOVERY_V1: true`. **Established compatibility contract from exact source:** `mobile-app/web/api.js` attempts Native HTTP for 15 seconds; only a transport error/timeout can invoke exactly one same-body WebView fallback (12 seconds). The same `refreshToken`, `storeId` and `__diagnosticTraceId` are reused. `src/sessionTokens.js` computes the next refresh token from the server-secret HMAC, stores its hash through a tenant-isolated CAS, and permits recovery with the immediately preceding refresh token only if it matches the present rotated hash and `last_used_at` is within 45 seconds. Both `src/index.js` and `src/gasApi.js` call this same `rotateSession` function. Definite application HTTP 503 does **not** cause an extra rotation attempt. If an ambiguous fallback returns `invalid_refresh_session` (e.g. an older Worker that already rotated on the first request), the client now **keeps** its currently stored credentials and reports the error, instead of erasing them on an unproven replay rejection. This safeguard does not mean an old Worker can automatically recover a lost reply: compatible server code must be deployed before distributing a new client that depends on automatic recovery.

## Executed incident fault-injection regression (2026-11-15, source-only)

### Two-part permanent architecture: prevention first, bounded recovery second

**Design intent from user clarification:** Do not call an automatic retry alone a root fix. Prevent the original foreground outage in the first place, *and* recover without task kill when a genuine transport/storage fault nevertheless occurs. A network-dependent request itself can fail for external reasons; the requirement is that a recoverable refresh failure must not unnecessarily freeze a previously authorized POS screen.

- **PREVENT:** iOS/Android share native `CapacitorHttp` refresh instead of the old 4,500ms WebView fetch; independently bounded deadline; a one-flight early renewal ~2 minutes before token expiry. **Newly fixed additional root-level coupling:** even with a valid 30-second access token, `API.post('checkToken')` had been synchronously waiting for a potentially stalled 30-second native refresh because the token was within the global 60-second renewal window. It blocked a permission check that could safely use the still-valid token. For *native checkToken only*, when access remains valid beyond the permission request's own timeout plus a safety margin, verification now goes straight to the authoritative server and kicks off one coalesced background refresh, with shared retry cooldown after error. If access is too close to expiry or already expired, no bypass occurs: the caller must await a usable refreshed token. This is applied once in shared `mobile-app/web/api.js`, not per screen; Android inherits it. Other protected business writes retain their stricter preflight renewal.
- **RECOVER:** A true refresh/network/Native bridge failure preserves refresh capability unless server explicitly invalidates it; previously verified documents get a non-blocking warning and retry while cold unauthorized documents stay gated; temporary storage failures have a persistence fence; correlated failures remain locally queued and are delivered via a healthy alternate transport with ACK. A 45-second response-loss replay is implemented server-side; the version-gated same-body **client recovery is now ON in source** (see activation section above), with actual deployed Worker compatibility not yet independently proven.
- **Executed red→green proof for newly found prevention defect:** Added `prevention: protected screen with 30s valid access token never waits for a stuck native refresh` to `test/ios_webview_auth_incident_integration_test.mjs`. Before code fix, 4/5 passed and this exact case failed with `STILL_WAITING`; after code fix, **5/5 PASS**. ## SecureStorage bridge stall containment and late-response recovery (follow-up)

- `mobile-app/web/native-auth.js` now reports `NativeAuth.status().bridgeStalled` on a timed-out SecureStorage write. The serialized native operation remains the exclusive writer, but new writes fail promptly with `secure_storage_bridge_stalled` instead of accumulating indefinitely. `NativeAuth.flush()` is bounded by the existing 4.5s deadline. Runtime logout still clears session data synchronously and leaves `nativeLogoutPending` as a durable fail-closed fence.
- A timed-out write invalidates its credential `authEpoch`; the late callback cannot clear the logout fence or claim current credentials persistent. If the native promise **actually settles** later, the shared queue first finishes every earlier admitted operation. At most one automatic repair then persists the **latest active** access+refresh token pair, or, if the user logged out, retries Keychain/Keystore credential cleanup. The fence is cleared only after confirmed successful pair persistence or complete cleanup.
- An access-only `setToken` must not clear a fence held because an earlier refresh pair was incompletely persisted; successful `setSession` of the full pair is required. This avoids a false restore of an old refresh capability after application restart.
- Added targeted fault-injection to existing `test/native_auth_test.mjs`: permanent native hang -> bounded fail-fast/flush, late native release -> serialized safe pair repair, logout during hang -> post-release safe cleanup, and incomplete pair -> access-only fence retention -> confirmed full-pair recovery. Final source-only NativeAuth suite **129/129 PASS** (versus pre-follow-up 122), with no formal device run.
- **Not guaranteed:** When native SecureStorage remains permanently unresponsive there is no safe in-process mechanism for forcibly cancelling an already executing native write using this plugin. It stays quarantined; authentication after a cold restart may require a fresh login. Do **not** remove the queue lock early and run parallel writes. A future native-plugin-level cancellation or generation-aware atomic storage API would be necessary to guarantee bounded automatic durable recovery in that extreme OS failure mode.
